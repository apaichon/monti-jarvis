# TASK-0178: Dedicated PostgreSQL Read-Only Role and Read Pool

## Outcome

Separate selected AI/reporting read traffic from mutation authority using a
least-privilege PostgreSQL role and explicit Go pool routing.

## Acceptance criteria

1. Migration or deployment SQL grants the read role only `CONNECT`, schema
   usage, and approved table/view `SELECT`; no DML, sequence write, or DDL.
2. Production startup verifies the configured read role is distinct from the
   writer authority without logging connection secrets.
3. Selected read handlers use the read pool explicitly and mutations remain on
   the writer pool.
4. A fixture test proves INSERT/UPDATE/DELETE/DDL fail under the read role and
   approved reads succeed.
5. Pool shutdown, timeout, and unavailable-read-role behavior are safe and
   observable without leaking SQL or credentials.

## Implementation update

Implemented in isolated worktree commit `feature/TASK-0178-db-capability-separation`:

- Separate Postgres KM-read and ticket-write pools with production fail-closed

## API-to-database-user routing

| API path | Database principal | Permission boundary |
| --- | --- | --- |
| `POST /api/chat`, `GET /ws/voice`, tenant preview chat/voice KM lookup | `monti_ai_km_ro` | `SELECT` only on approved KM/context projections; no ticket or KM mutation |
| `POST /api/tenant/km/*` management writes | `monti_km_rw` / existing writer path | KM ingest/update only, subject to tenant policy; never used by AI retrieval |
| `POST /api/customer/tickets`, ticket events/status | `monti_ticket_rw` | Ticket tables/events and scoped source lookup; no KM writes or cross-tenant access |

The shared-database deployment uses capability-specific roles plus RLS and
transaction-local tenant context. A dedicated-database deployment may also
provision tenant-specific principals, but credentials must never be reused
across tenants.
