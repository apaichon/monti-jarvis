# TASK-0215: Context Panels, Mobile Rows, and Visual Verification

## Outcome

Tenant, customer, device, about-customer, and quick-action context surfaces are
available without distracting from the active call, and Sprint 59 closes with
desktop/mobile visual evidence.

## Done Notes

Added the right-side insight rail and mobile context rows. Verified with
`npm run check`, `npm run build`, and Playwright screenshots for desktop
dark/light plus mobile dark using mocked public/customer APIs. Refined the
desktop left rail into compact icon-led tenant, customer, and device accordions;
the summary row remains visible when details are collapsed, and device controls
retain refresh, selection, and audio-test behavior. All context accordions now
start collapsed. The center conversation workspace uses bounded avatar sizing
and independent vertical scrolling so the greeting, listening state, call/end
controls, transcript, and composer remain reachable at shorter desktop heights.

## Acceptance Criteria

1. Desktop left rail shows Monti branding/status, tenant info, customer info,
   device settings, and help/settings rows using existing safe data.
2. Desktop right rail shows about-customer and quick-action panels without
   requiring new backend APIs.
3. Mobile shows tenant, customer, and device rows below the composer and keeps
   them tappable.
4. Missing customer/context data has a clean unavailable or omitted state.
5. Visual screenshots are captured for desktop dark, desktop light, mobile dark,
   and mobile light.
6. `apps/customer-web` passes `npm run check` and `npm run build`.
7. Manual smoke verifies start call, text send, mute/unmute, end call, audio
   device selection, and EN/TH/JA label fit.
8. Desktop context sections use recognizable icons, expose their expanded state
   to assistive technology, and collapse without hiding the section summary.
9. The center workspace never clips call controls; overflow produces a usable
   vertical scrollbar while the composer remains reachable.

## Notes

- Do not add new customer-history APIs in this sprint.
- Reuse existing tenant/customer/session fields; placeholders must be honest and
  not imply unavailable data is real.
