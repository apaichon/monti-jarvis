# TASK-0179: Tenant-Scoped Policy, Query Allowlists, and Isolation Enforcement

## Outcome

Make tenant scope request-local, bounded, and denied by both application
authorization and database policy on the prioritized high-risk read paths.

## Acceptance criteria

1. Tenant context comes from the authenticated subject, is set with
   transaction-local configuration, and cannot persist across pooled requests.
2. Selected tables/views have deny-by-default tenant policies and an explicit
   migration/policy inventory.
3. Limits, offsets, sort fields, identifiers, and filter values are bounded or
   allowlisted; no string-concatenated user SQL remains in touched paths.
4. Two-tenant tests prove tenant A cannot read, mutate, or infer tenant B's
   protected records through API, read pool, or reporting paths.
5. Missing/invalid tenant context fails closed with a safe authorization error.

## Principal isolation contract

1. `monti_ai_km_ro` is bound to the authenticated tenant context for every
   `/api/chat` or `/ws/voice` KM retrieval.
2. `monti_ticket_rw` is bound to the authenticated tenant context for ticket
   creation and ticket-event writes; it cannot use the AI KM read path to
   widen access.
3. Tenant A credentials, role mappings, and transaction context cannot return
   Tenant B rows, even when a caller supplies a different tenant ID in a
   query, header, or body.

## Implementation update

Implemented in the isolated Sprint 41 worktree:

- Ticket reads and writes set `app.tenant_id` with `SET LOCAL` inside a
  transaction.
- Ticket and ticket-event tables use `FORCE ROW LEVEL SECURITY` policies in
  the capability-grants migration.
- KM document/chunk reads and writes also set `app.tenant_id` in a transaction;
  the KM read pool is restricted by `FORCE ROW LEVEL SECURITY` policies.
- Missing tenant context fails closed.

The implementation is committed with TASK-0178 in the shared security branch;
database-backed two-tenant fixture verification remains pending.
